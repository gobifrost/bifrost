# Baseline: execution times and memory (2026-10-27)

The first reference run of the benchmark suite
(`docs/superpowers/specs/2026-10-27-performance-benchmark-suite-design.md`).
Later changes, starting with agent runs moving back to workers, are compared
against these numbers.

**Reproduce:**

```bash
./test.sh bench up
./test.sh bench run --profile baseline --backend fake
./test.sh bench run --profile baseline --backend deepseek   # key via op-personal
```

## Conditions

- **Build:** `main` at `1fab1d0db` plus benchmark-only commits (harness `05b73965a`). The production
  Dockerfile image was built locally. The image under test contains no product
  change.
- **Topology:** like production. One API replica (1 CPU / 1 GiB limit),
  `MALLOC_ARENA_MAX=2`, no scheduler, worker capacity from API-launched worker
  Jobs (warm 1, max 2, 2 GiB, 2 CPU limit), Postgres, PgBouncer and Redis.
  SeaweedFS stands in for object storage.
- **Data:** 1,851 seeded workflows, tools and data providers (production's
  active counts), plus 200 bench documents.
- **Host:** Kind on one 8-core, 62 GB workstation. Transparent huge pages are
  `madvise` here and `always` in production.
- **Method:** each class ran 10 sequential runs, then three bursts of 10
  concurrent runs, in two passes. Times are the platform's own timestamps.
  API memory is read from `/proc/1/smaps`; container memory comes from the
  kubelet.
- **Repeatability:** two fake-model runs agree within ±9% on sequential p50
  times (the largest gap is 7 ms on `wf-noop`). Fresh API memory agreed within
  0.2 MiB.

## Execution times (end-to-end, ms; mean of the two passes)

| Class | What it does | Fake model: alone p50 / p95 | Fake: 10 at once p50 / p95 | DeepSeek: alone p50 / p95 | DeepSeek: 10 at once p50 / p95 |
|---|---|---:|---:|---:|---:|
| `wf-noop` | Nothing: platform overhead | 87 / 122 | 485 / 784 | 80 / 98 | 575 / 920 |
| `wf-sdk` | 5 config reads, 1 table query, 1 insert | 214 / 272 | 1,769 / 2,302 | 208 / 244 | 1,753 / 2,347 |
| `wf-wait` | 2 s external wait | 2,080 / 2,089 | 2,428 / 2,828 | 2,086 / 2,106 | 2,465 / 2,761 |
| `wf-cpu` | ~20 MB JSON build and parse | 8,716 / 8,829 | 31,967 / 41,432 | 8,760 / 8,936 | 32,143 / 42,165 |
| `wf-large` | ~5 MB result | 172 / 213 | 1,005 / 1,774 | 167 / 227 | 1,085 / 1,793 |
| `agent-chat` | One model turn | 164 / 635 | 932 / 2,029 | 1,889 / 2,633 | 2,434 / 3,048 |
| `agent-tools` | Three workflow tools, direct | 634 / 744 | 5,436 / 6,114 | 3,700 / 7,774 | 6,240 / 9,253 |
| `agent-codemode` | Same tools via CodeMode | 655 / 880 | 5,888 / 6,673 | 3,910 / 6,516 | 7,687 / 8,581 |

Queue wait, alone, was 25–45 ms for every class. Every one of the 1,280 runs
across both backends succeeded. DeepSeek agents took 2–3 model turns and used
2–4k tokens per tool-using run.

## Memory (MiB)

| Point | API process | API heap | Worker Jobs |
|---|---:|---:|---|
| Fresh, empty | 349 | 94 | 78 + 78 |
| Booted on seeded data | 349–352 | 94 | 78 + 78 |
| After the workflow classes | 380–384 | 109 | 78 + 78 |
| After the first agent class | 420–422 | 121 | 78 + 78 |
| Settled, fake model | 420 | 110 | 78–79 each |
| Settled, DeepSeek | 438 | 121 | 78–80 each |

Idle tenant working sets at the end of the DeepSeek run: API 408, two worker
Jobs 80 + 78, Postgres 411, Redis 9, PgBouncer 9. That's **about 1 GiB
excluding object storage** (SeaweedFS used another 105 MiB; hosting would use
managed storage).

## Findings

1. **Agents contend inside the API.** Alone, a fake-model tool-using agent run
   takes about 0.65 s; ten at once take about 5.4–5.9 s each, roughly 9×.
   They all share the API's one CPU and event loop. With DeepSeek, a burst adds
   2.5–3.8 s per run. This is the case for moving agent runs to workers
   (`docs/superpowers/specs/2026-10-27-agent-runs-on-workers-design.md`).
2. **SDK calls serialise through the API.** One `wf-sdk` run (7 SDK calls)
   takes about 210 ms. Ten at once take about 1.75 s each, roughly 8×. Every
   workflow's SDK call goes through the one API process.
3. **CPU-bound workflow code runs about 10× slower than plain Python.** The
   `wf-cpu` work takes 0.84 s in plain Python on the same image and 8.7 s as a
   workflow. The execution engine's `sys.settrace` variable-capture hook
   (`api/src/services/execution/engine.py`, since December 2025) returns
   itself for every frame, so every executed line runs a Python callback. It
   only needs the workflow's final return. This is the largest single
   execution-time cost measured.
4. **The agent runtime adds about 40 MiB to the API the first time any agent
   runs,** and DeepSeek runs add about 18 MiB more than the fake model.
5. **Worker Jobs idle at 78–80 MiB** and don't grow across 1,280 runs.
6. **The local API settles near 440 MiB; production sits near 790 MiB.** Its 480 agent
   runs (240 against DeepSeek) did not reproduce production's ceiling. Production's remaining ~350 MiB comes from load these classes
   don't yet model: production agents with large prompts, 609 bound tools and
   real tool payloads, MCP clients, UI users, many hours of uptime, and
   huge-page `always` nodes. The production evidence (memory steps
   following agent-run starts) remains in the investigation notes. Moving
   agents out of the API removes that whole category, whatever the exact
   number turns out to be.

## Limits

- Single-host Kind: absolute times are good for comparisons between builds on
  this host, not as cloud capacity numbers (Phase 3 calibrates on DOKS).
- Bursts are 10 concurrent runs; this is not yet a capacity search (Phase 2).
- Production's transparent huge pages `always` setting is not reproduced
  (`thp_emulation` is available but was off for this baseline).
