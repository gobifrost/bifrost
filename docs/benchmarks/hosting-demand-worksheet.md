# Hosting Demand Worksheet

Use this worksheet with SHA-pinned, matching campaign, soak, profile, harness,
and runtime-image evidence. It is a commercial-input template: it does not
forecast customer demand from a saturation result or establish capacity per
customer. A customer quote also requires a passing campaign and cloud
calibration for the selected region and topology.

For each row, define whether the monthly demand is fleet-wide or per tenant.
If it is per tenant, multiply successful external requests and retained stocks
by placements; if it is fleet-wide, do not multiply the request volume. A
passing capacity rate, if one exists, is a guard on the declared peak rate
after explicit headroom; it is not a demand estimate.

Record failed, cancelled, timed-out and retried attempts alongside successful
requests. They can generate logs, retained results and provider charges without
adding revenue. The synthetic soak normalizes growth by durable terminals,
including failures, while the illustrative calculator scales by successful
external-request demand. Use that projection only with an explicit comparable
failure/retry mix; otherwise budget the extra attempts separately and leave the
customer projection unpriced. Queued or unfinished work needs a separate stock
and recovery assumption.

## 30-Day Data and Retention Inputs

Keep billing stocks distinct. Generated WAL is a flow, retained WAL is a stock,
and database logical bytes, index/TOAST bytes, WAL, and allocated database disk
must not be added together. Short synthetic-soak growth is illustrative until
representative demand, data entropy, retention, audit, and reclamation are
measured.

| Stock or flow | Per-tenant input | 30-day projection | Billing treatment |
|---|---:|---|---|
| PostgreSQL volume | Provisioned GiB: `20` minimum for the declared PostgreSQL component | `placements × provisioned GiB` | Bill provisioned GiB, never logical bytes or namespace storage quota. |
| Logical database/result data | Initial GiB: `null`; representative result bytes per successful external request: `null` | `(initial + result/DB growth × successful external requests) × retention reserve` | Planning stock only; does not reduce provisioned-volume cost. |
| Generated and retained WAL | Generated bytes/request: `null`; retained WAL GiB and policy: `null` | Record the flow and retained stock separately | Price retained storage/backup only when a dated unit price is known. |
| Object payload and versions | Current payload GiB: `null`; retained versions/delete markers GiB: `null`; growth/request: `null` | `(current + versions + object growth × successful external requests) × retention reserve` | Apply object subscription, excess GiB, egress, and request fees separately. |
| Audit/artifact retention | Initial GiB and growth/request: `null`; retention days: `null` | `initial + growth × retained request population` | Keep separate from workflow-result and database estimates. |
| Container/application logs | Initial GiB and growth/request: `null`; rotation/retention policy: `null` | `initial + growth × 30-day activity` | Include observability/log ingestion and retained-log charges. |

Use retained backups as a separate stock: `placements × retained backup GiB per
tenant`. Do not assume deletion or vacuum immediately reclaims filesystem or
object-store allocation.

## Placement and Availability Inputs

| Input | Current known value | Required worksheet entry |
|---|---|---|
| Maximum tenant CPU / memory requests | 4 GB envelope: `3900m` CPU / `3.53 GiB`; M: `3900m` / `7.69 GiB` maximum occupancy | Per-tenant maximum requests, not average observed use |
| Actual node allocatable resources | One October 31 snapshot: `3890m` CPU / `6568236Ki` memory | Dated allocatable CPU/memory for every selected node pool/region |
| Existing reservations | Snapshot: `1323m` CPU / about `2.71 GiB` requested by other namespaces | Other requests, system reserve, spare capacity, pod/PVC limits |
| Placement result | The 3900m benchmark envelope cannot fit that observed node, before other requests | `floor(min(available CPU / tenant max CPU, available memory / tenant max memory, pod/PVC/storage limits))` |

The snapshot is not a general overhead estimate. CPU/memory maxima, allocatable
resources, reservations, HA minimum nodes, and idle/spare capacity must all be
explicit before calculating node count. Observed runtime consumption is useful
for comparison, but placement uses maximum permitted requests. No value in this
table supports a tenant-density or per-customer-capacity claim.

Builds need a separate placement and concurrency budget. The interactive
fixture builds with execution workers drained, then restores the runtime policy
before measuring app actions. That procedure does not establish app latency or
capacity while builds and workflows compete for the same resources. Record
maximum concurrent builds, their requested resources, queue delay, and whether
they use shared or tenant nodes before pricing their headroom. Include scheduled
platform maintenance and shared scheduler services in the same allocation.

## Revenue and Margin

Use external successful requests for per-success denominators:

```text
external successful requests = workflow successes + agent-request successes
all-in cost per successful request = all-in cost / external successful requests
gross margin dollars = revenue - all-in cost
gross margin percent = (revenue - all-in cost) / revenue × 100
```

Nested tool terminals remain visible operational work, but are excluded from
the external-request denominator unless they are separately sold and priced.
Revenue, price plans, discounts, taxes, payment fees, and labor allocations are
`null` until actual commercial inputs are supplied; do not calculate a margin
from a blank or nonpositive revenue denominator.

See the [measurement contract](measurement-contract.md) for the evidence and
denominator requirements used by the hosting calculator.
