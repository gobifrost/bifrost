## Outcome and authority

The API accepts durable work and orchestrates execution capacity. Workflow executions, agent runs and PlatformJobs share an internal attempt lifecycle and registered handlers. Kubernetes workers start from zero, execute multiple jobs using isolated children, remain available for more work during a configurable idle period, and drain back to zero. Heavy or incompatible work can use one-attempt pods through the same framework. The API remains available for HTTP, WebSockets, trigger leadership, dispatch and recovery. The final Kubernetes deployment needs no dedicated scheduler or fixed legacy worker fleet.

This is the user's October 22 clarification of the October hosted-runtime proposal. It supersedes the September spike's requirement for a resident control scheduler and its assumption that KEDA owns worker scaling. Preserve supported Docker behavior through staged opt-in configuration. A common attempt format does not replace public Workflow/Execution, AgentRun or PlatformJob records, permissions or status contracts.

## Runtime design

1. **Durable acceptance.** Commit the domain record and durable dispatch intent atomically. A request may return once acceptance is durable; it never waits for a Kubernetes create call. PostgreSQL is authoritative for pending payloads, delayed work, attempts, leases and recovery. Redis notifications or PostgreSQL NOTIFY can wake controllers, with bounded reconciliation covering lost notifications. Redis-only expiring payloads and NOTIFY alone do not provide durable acceptance.
2. **API control.** Extract lifecycle-managed asynchronous services; reuse the API's database initialization and shutdown. One installation-scoped, database-time fenced trigger leader handles recurring schedules. Replicas can dispatch/reconcile concurrently through atomic per-attempt and capacity claims. A lease loss stops trigger production; occurrence deduplication covers failover, timezones, DST and catch-up. Heavy handlers remain outside API processes. Bound DB connections, reconciliation batches and Kubernetes calls so control work cannot starve HTTP/WebSockets.
3. **Shared attempts.** Retain domain ownership and authorization while sharing handler/version, payload reference, resource class, placement, image/package generation, attempt identity, lease/fence, progress, cancellation, deadlines and terminal outcome. Persist placement/version for in-flight work. Waiting parents release execution slots while durable children run; nested work cannot exhaust all capacity and deadlock its parents.
4. **Reusable Kubernetes workers.** Initial recommendation: one controller-created `batch/v1 Job` for each bounded worker lifetime. Its one pod can accept successive compatible attempts, each in a fresh isolated child. This reuses Job launch/UID fencing and lets idle workers finish without a Deployment immediately recreating them. Preserve the suspended-create -> persist returned UID -> UID-bound unsuspend protocol for both placements. Use `parallelism=1`, `completions=1`, `restartPolicy=Never`, `backoffLimit=0` and terminal TTL cleanup. A Job can still start a program twice, so bind one admitted worker incarnation to the persisted Job/pod UIDs and fence every claim. Associate capacity with stable installation identity, not an initiating API pod's garbage-collection lifetime. Worker lifetime success means capacity retired; domain attempts have independent outcomes.
5. **Idle and drain.** Trial idle timeout: 300 seconds, configurable and validated against arrival patterns; minimum reusable capacity defaults to zero. Reset the idle timer when eligible work arrives. Atomically change `ready -> draining` only with no assigned/running/reserved attempts, then stop claims and exit. A concurrent enqueue must either cancel retirement safely or launch replacement capacity. Bounded maximum lifetime triggers drain, not termination of active work. Do not copy a one-attempt Job's short deadline onto a reusable worker. Rollouts and scale-down use explicit drain acknowledgement; forced loss follows fenced recovery policy.
6. **Demand and admission.** Match durable queued work to ready slots and pending worker reservations by resource class/package generation. Reserve starts atomically so API replicas do not over-launch; count starting, unschedulable, ready, busy and draining pods toward their appropriate ceilings. Start more workers as slots fill or queue age exceeds policy. Reserve capacity for interactive/system work and apply per-org, per-class, total CPU/memory, DB-connection and provider ceilings. Start with one active attempt per reusable worker, then increase only with measurements. Worker/pod caps and the infrastructure node cap are different settings.
7. **One-shot placement.** Use isolated one-attempt Jobs for build/heavy/incompatible handlers, sharing the attempt contract, cancellation, recovery and diagnostics. Pin image digest and package/environment generation. Bifrost owns retries. An ambiguous create is reconciled using the durable launch identity; it never causes an unfenced second launch or a silent local fallback.
8. **Resources and node integration.** Measure supervisor/SDK baseline plus execution peak, CPU, scratch and startup costs for small/standard/build/heavy profiles. Queue pressure grows the number of pods. Kubernetes node autoscaling reacts when resource requests cannot fit; a running pod does not gain memory because work grows. OOM escalation requires an explicit safe retry policy, not blind replay of external actions. Preserve the installation's existing node maximum; do not raise it to make a test pass. Warm tails on shared Kubernetes nodes release capacity, but do not imply per-invocation cloud billing or zero cluster cost.
9. **Security and SDK.** Keep infrastructure privileges in the API/controller identity, with namespace-scoped RBAC for managed Jobs/pods and admission-restricted templates. Worker credentials are limited to their installation, incarnation, allowed handlers/classes and claims; they cannot edit Kubernetes objects. Untrusted child code receives short-lived attempt-scoped SDK access, without DB, Redis, broker, signing-key or infrastructure credentials. Existing build Jobs use broad `envFrom` secrets: that is an explicit migration gap, not a template for general untrusted runners. Preserve the worker-local SDK authorization/offload boundary and measure its memory. Resolve worker-local versus API SDK serving within these roles; a separate permanent SDK host is not assumed. Isolate packages, writable state and per-attempt identity between reused executions.
10. **One scaling owner.** API-owned capacity reconciliation controls these worker Jobs. Flux owns templates, images, RBAC, quotas and policy ceilings; it must not prune runtime-created Jobs or revert dynamic desired state. HPA/KEDA must not compete for ownership of the same capacity. Watch owned Kubernetes objects for changes and use a bounded resync for repair. DOKS retains responsibility for node provisioning/consolidation.

## Acceptance and validation

- **Real zero/reuse/burst:** Kind begins with zero execution pods and no dedicated scheduler. Enqueue each public work family; capture worker Job/pod UID, attempt IDs and timing. Submit more work before idle expiry and prove the same worker handles it in fresh children. Fill slots, observe bounded additional workers, then reach zero with no active/reserved claims. Simultaneous API dispatchers, idle expiry and new work must not lose or duplicate ownership.
- **Recovery:** kill the trigger leader, restart all API replicas, kill a worker, force node loss, interrupt launch after each persisted step, simulate Kubernetes throttling/outage and unschedulable pods, cancel queued/running work, and force OOM. Verify durable status, stale-owner rejection, orphan cleanup and retry eligibility. Lease fencing cannot guarantee exactly-once external side effects: use idempotency/checkpoints or an explicit operator recovery outcome, and account for an old runner before unsafe replay.
- **Compatibility:** preserve scheduled/deferred work, SDK-triggered nested work, synchronous data-provider/form/HTTP deadlines, delegated agents, live WebSocket progress, App/SDK builds and Solution deploys. A synchronous caller gets a clear bounded capacity outcome if cold start cannot meet its deadline. Verify CLI success and a controlled failure's nonzero exit; reproduce the reported exit-code issue before fixing it. Exercise supported Docker and mixed-version upgrade/drain/rollback paths.
- **Security:** cross-org access denied; a revoked/stale attempt cannot call scoped SDK endpoints or finish a new attempt; untrusted children cannot read platform credentials; reused workers cannot expose prior attempt state/packages beyond policy. Do not execute real customer side effects in fixtures.
- **Operations and cost:** report queue age, admission reason, class, worker state, attempt/Job/pod correlation, cold-start/import/package time, image pull, p50/p95/p99 queue-to-start, cgroup peak/OOM, pool wait and API latency during bursts. Measure idle tail versus startup savings and node usage. Structured capacity errors remain visible through existing domain diagnostics; provider detail belongs in admin views.
- **Local checks:** use Docker-backed `./test.sh`, focused runtime/lease/controller/consumer tests, `./test.sh quality api`, relevant CLI/DTO contract tripwires, manifest/RBAC checks, and a focused browser acceptance flow if Settings/progress UX changes. Existing tripwires include `test_kubernetes_build_controller.py`, `test_platform_job_kubernetes_client.py`, `test_kubernetes_build_manifests.py`, `test_kubernetes_spike_manifests.py`, `jobs/platform/test_kubernetes_runner.py`, `jobs/schedulers/test_platform_jobs.py`, `services/test_platform_jobs.py`, and `test_contract_version.py` under `api/tests/unit/`. Extend the existing Kind harness (`./test.sh kubernetes ...`) for the new runtime. Record exact commands/results; the merge queue owns broad suites.
