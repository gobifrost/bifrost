# Phase 4 test collection and proposed tools readiness inventory

Status: **UNAPPROVED inventory/proposal**. This is a bounded source inventory for Phase 4 readiness only. It proposes the smallest next seams for agent-wide test collections, simulation-only proposed tools, and designer generation from explicitly selected authorized findings/evidence. It does not approve implementation, UI work, runtime redesign, or new job/status infrastructure.

Source basis:

- Master Phase 4 requirement: `docs/superpowers/plans/2026-09-20-unified-agent-quality-workbench.md` requires a default test collection, latest results per mode/profile/version, versioned portable definitions, simulation-only tools, candidate binding, matrix comparisons, and a production apply guard.
- Evaluation data model: `api/src/models/orm/agent_evaluations.py`.
- Evaluation contracts/routes/services: `api/src/models/contracts/agent_evaluations.py`, `api/src/routers/agent_evaluations.py`, `api/src/services/agent_evaluations/`.
- Findings data model/routes/contracts: `api/src/models/orm/agent_findings.py`, `api/src/models/contracts/agent_findings.py`, `api/src/routers/agent_findings.py`.

## Minimal corrected contract for the next implementation packet

1. **Agent-wide tests as implicit default authoring collection**
   - No primary-membership table and no user-facing mark-primary workflow.
   - Creating a test from the agent-wide surface writes an accepted/draft case into a server-owned default origin suite for that agent/org when no named suite is specified.
   - Named suites remain origin metadata and optional advanced grouping.
   - Logical test identity for latest reads is the concrete accepted case version: `(case_id, case_version)`, with origin suite metadata included for display/partitioning.

2. **Latest results include simulation and recorded modes**
   - `mode=simulation`: read `AgentEvaluationResult` joined to `AgentEvaluationExecution`.
   - `mode=recorded`: read `AgentRecordedEvaluationResult` joined to `AgentRecordedEvaluation`.
   - Baseline/candidate comparison is a separate dimension from mode.
   - Tested execution profile is `AgentEvaluationExecution.profile_id`; semantic judge profile/config is judge provenance and must not be used as the tested profile.

3. **Subset simulation admission gap**
   - Add explicit selected-case admission for simulation before implementing agent-wide Run All.
   - The selected set must include case versions, not only case IDs, so reruns cannot silently pick a newer edited version.
   - Existing suite/matrix admission executes all accepted enabled cases and cannot be used directly for selected subsets.
   - Active dedupe needs a subset fingerprint in addition to suite/version/candidate/profile/repetitions.

4. **Recorded Run All reuse**
   - Reuse `RecordedEvaluationCreate.case_ids` and `_load_cases()` for recorded selected tests.
   - Agent-wide test selection must pass explicit selected cases; `all_tests=true` remains an explicit all-published-tests choice, not a substitute for UI-selected versions.

5. **Proposed tool contracts**
   - Proposed tools must include input and output JSON Schema contracts plus simulation behavior.
   - They are simulation-only snapshot metadata with no workflow UUID, no `target_id`, and no production executor binding.
   - Output schema validation belongs in the simulator/proposed-tool behavior path; existing runtime `output_schema` validates final agent invocation output, not individual tool return contracts.
   - Apply is blocked while unresolved proposed tools remain. Resolution is a later explicit create/map action through normal workflow/tool creation, not implicit during tests.

6. **Finding/evidence generated tests**
   - Explicit authorized user selection is the approval for generating/creating the test.
   - Dismissed findings are still selectable if the user has access; dismissal does not erase the usefulness of a regression test.
   - Every source finding/review/run/evidence reference must be reauthorized at generation and on later reads that expose derived evidence. Missing/revoked source fails closed.

## Genuine unresolved decisions

- **Default origin representation:** the smallest user model is an implicit default suite per agent/org, but implementation must decide whether to create it lazily, hide it from ordinary named-suite lists, and how to label it in CLI/API responses.
- **Subset execution schema:** simulation execution currently stores one suite/version and all frozen cases. A subset fingerprint can avoid dedupe collisions, but the public execution DTO may also need to expose selected case count/source to make results understandable.
- **Recorded latest grouping:** recorded results are per `(evaluation_id, case_id, run_id)`. The latest read model must decide whether to show latest per recorded source run, latest aggregate across selected runs, or both.
- **Proposed tool behavior language:** input/output schemas are clear, but the allowed behavior format should be the existing fixture/rules vocabulary unless a later packet approves a richer simulator behavior DSL.

## Follow-up: Create/Edit Test without suite setup or publish

Current source facts:

- `create_suite()` creates a draft `AgentEvaluationSuite` with `version=1`; `publish_suite()` only flips `status='published'` and does not clone cases or increment suite version.
- `update_suite()` is blocked once `suite.status == 'published'`; draft suite metadata edits increment `suite.version`.
- `create_case()` is blocked for published suites and creates an accepted `AgentEvaluationCase` row with `version=1`.
- `update_case()` is blocked when the suite is published or the case is already accepted. The error text says accepted versions freeze as new versions, but this route does not create the new version.
- `accept_case()` is also blocked for published suites. It accepts an unaccepted draft by inserting a new `AgentEvaluationCase` row through `accept_proposal()`, then sets `case.version = max(existing accepted sibling versions with the same suite_id/name) + 1`.
- There is no `parent_case_id`, `logical_test_id`, `supersedes_case_id`, or lineage table in `AgentEvaluationCase`. The only lineage-like convention is `(suite_id, name, version)` and the accepted-case uniqueness constraint `(suite_id, name, version)`.
- Old results point to the concrete row ID and version: `AgentEvaluationResult.case_id/case_version` and `AgentRecordedEvaluationResult.case_id/case_version`. Because accepted revisions are inserted as new rows, old result identity is preserved, but there is no durable “same logical test” ID for latest-result rollups across revisions except name matching within one suite.

This means the previous “implicit default origin suite” idea is not sufficient by itself. If the default origin suite is published, users cannot create/edit tests. If it stays draft, current simulation execution rejects it because `create_execution()` and batch admission require `suite.status == 'published'`. If edits create a new accepted row, latest-result grouping still needs stable logical identity beyond name matching.

| Option | Contract | Benefits | Costs / blockers |
| --- | --- | --- | --- |

Old results keep pointing at old case rows; latest views group by `logical_test_id` and show current accepted version. | Smallest stable identity fix. | B. Add separate test-definition table | Add `AgentEvaluationTestDefinition(id, agent_id, org_id, origin_suite_id, name, current_case_id, created_at, updated_at)` and keep case rows as immutable versions. | Clean logical object model for agent-wide tests and portability. Can represent tests across suites and origin metadata explicitly. | More schema/API surface than needed for the immediate blocker. Risks becoming a parallel case system if not tightly constrained. |
| C. Use `(suite_id, name)` as logical identity | Do not add schema; latest groups by suite and case name, version by max version. | No migration. | Not robust. Recommended next packet should choose **A** unless primary wants the larger definition object. It is the narrowest way to let agent-wide Create/Edit Test feel suite-free while preserving named suite immutability and old result references.

### Default authoring collection with stable test identity

Proposed minimum if Option A is accepted:

1. A default collection is a server-managed `AgentEvaluationSuite` row per `(org_id, agent_id)` with reserved name/metadata. It remains hidden from ordinary named-suite lists unless explicitly requested as origin metadata.
2. Users creating a test from the agent-wide surface do not select a suite; the API finds or creates the default collection and inserts an accepted case with a new `logical_test_id` and `version=1`.
3. Users editing an accepted test do not mutate the old case row. The API inserts a new accepted case row with the same `logical_test_id`, incremented version, copied origin metadata, and updated fields. Existing results remain attached to old `(case_id, case_version)`.
4. Named suites stay immutable after publish. Editing a case whose origin is a published named suite from the agent-wide surface should either: create the next logical version in the default collection while preserving `origin_suite_id` as prior origin metadata, or be rejected with “copy to default collection to edit.” This is an open product decision because current schema ties a case to exactly one suite via non-null `suite_id`.
5. Agent-wide Run All selects current accepted versions by `logical_test_id`, then uses subset simulation/recorded admission. It does not require the default suite to be published as a user-visible step.

### Publish requirement alternatives

The current execution routes require published suites because suite publication is the human “freeze before run” step. Agent-wide Create/Edit Test removes that visible step, so one of these must be explicit:

- **Default suite auto-published with immutable case-version inserts:** keep the default suite status published after creation but add narrow server-owned endpoints that may insert new immutable accepted case rows into default suites. Ordinary suite case CRUD remains blocked for published suites. This preserves “published means existing contents are immutable,” while allowing append-only versions through the agent-wide test API.
- **Subset admission bypasses suite status for default suites only:** allow execution of selected accepted case versions from a draft default suite. This is smaller at admission time but weakens the current meaning of draft versus executable and should be avoided unless primary accepts that policy.
- **No suite-backed default:** introduce a separate test-definition table. This avoids bending suite status semantics but is a larger redesign.

The least disruptive path is the first: keep default suite published and allow only append-only immutable case versions through the new agent-wide test service, never in-place edits.

## Concrete candidate apply / production guard locations

Existing apply surface:

- `POST /api/agents/{agent_id}/tuning-session/apply` in `api/src/routers/agent_tuning.py` is gone (`410`). The replacement apply path is the normal authorized `PUT /api/agents/{agent_id}` in `api/src/routers/agents.py`.
- `AgentUpdate` in `api/src/models/contracts/agents.py` accepts `system_prompt`, `tool_ids`, `delegated_agent_ids`, `system_tools`, `mcp_connection_ids`, model/profile/limits fields, and `change_reason`.
- `update_agent()` locks the agent row, enforces `If-Unmodified-Since`, validates tool/delegate/model references, applies relationship changes, and records `AgentPromptHistory` when prompt/config changes.
- Candidate snapshots are created by `create_candidate_endpoint()` and `create_candidate()` with `evaluation_only=True`. Production enqueue is guarded by `assert_production_snapshot()` in `api/src/services/agent_evaluations/candidates.py`, but `PUT /api/agents/{id}` does not consume candidate snapshots directly.

Therefore the proposed-tool guard must be placed at the production apply translation boundary, not only in runtime execution:

1. If a future “apply candidate” helper/API maps an `AgentCandidateSnapshot` to `AgentUpdate`, it must reject snapshots containing unresolved `simulation_only` proposed tools before calling `PUT /api/agents/{id}` or equivalent update logic.
2. If the UI/CLI applies by constructing `AgentUpdate` directly from a candidate, the server-side endpoint that performs that translation must be introduced as the only supported candidate-apply path; otherwise unresolved proposed tools could be silently dropped client-side.
3. `PUT /api/agents/{id}` already validates real `tool_ids`, `delegated_agent_ids`, `system_tools`, MCP grants, model profiles, and stale updates. It should remain the final production mutation path after proposed tools have been explicitly created/mapped to real workflow/system/MCP/delegation references.
4. Runtime guards (`assert_production_snapshot()` and synthetic snapshot markers) remain necessary but insufficient for apply, because production apply mutates the live `Agent` row rather than enqueueing an evaluation candidate snapshot.

## Open decisions for primary

1. **Stable identity:** approve `logical_test_id` on `AgentEvaluationCase`, or choose a separate test-definition table. Name matching is not sufficient for Phase 4 latest-result semantics.
2. **Default collection representation:** approve a hidden/server-managed default `AgentEvaluationSuite` per agent/org, or choose a separate definition object.
3. **Default collection publish policy:** decide whether default suites are auto-published with append-only immutable case-version inserts, or whether default accepted cases can execute from draft suites. The former preserves current published-suite semantics better.
4. **Editing named-suite tests from agent-wide UI:** decide whether edits create the next version in-place only while the named suite is draft, copy to default collection when named suite is published, or reject with an explicit “copy/edit in default tests” action.
5. **Candidate apply endpoint:** decide whether Phase 4 introduces a server-side “apply candidate” endpoint that translates candidate snapshots to `AgentUpdate` under `If-Unmodified-Since`. Without this, proposed-tool apply guards cannot be enforced reliably at the candidate boundary.
